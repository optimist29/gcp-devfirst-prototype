🚫 When NOT to use Cloud Run The Anti-Pitch
1.

Persistent local disk state: Containers are ephemeral. When an instance terminates, disk vanishes. Use Cloud SQL or GCS volumes.

2.

Flat 24/7 100% CPU loads: If your servers never sleep, Compute Engine VMs with Committed Use Discounts are ~3x cheaper per core-hour.

3.

20,000 idle WebSockets: WebSockets are supported (up to 60 min), but paying per container-second for mostly idle sockets gets pricey. Use Compute Engine or Pub/Sub push.

⚡ The Concurrency Advantage (Why Lambda users switch) 1 Container = 1000 Req

AWS Lambda provisions 80 separate execution environments for 80 simultaneous requests. Cloud Run multiplexes them into 1 container with shared database connection pools.

🚫 When NOT to use Spanner The Honest Trade-off
1.

Under 500GB in a single region: Cloud SQL for PostgreSQL is much cheaper and supports all native extensions. Use Cloud SQL.

2.

You rely on Postgres extensions: No PostGIS, no pg_vector, no custom C extensions. Spanner implements core SQL and wire protocol, not extension binaries.

3.

Sub-millisecond single-row reads: Strong consensus has a physical floor. Expect ~5–8ms p50 reads, not the ~0.5ms of local RAM/Redis.

🚪 How to Leave Spanner (Migration Honesty) Zero Gaslighting

Getting in is easy; getting out depends on what features you use. If you stay on the Postgres dialect, tables and schemas export 1:1 via Avro or standard CSV into Postgres. The real lock-in: If your application architecture relies on synchronous multi-region writes across 3 continents, no single-node database can replace it. Price that into your architectural decision.
